In Australia, physical address capture is standardized by Australia Post and the Australian Standard AS 4590 (Exchange of client information).

To ensure clean database entry and maximum compatibility with address validation APIs (like Australia Post's PAF/AMAS
data systems), your form should be structured to handle the unique quirks of Australian geography (such as unit numbers,
lot numbers, rural roadside delivery, and long suburb names).

Handling Units, Flats, and Apartments
The standard Australian convention for multi-unit dwellings uses a forward slash (a solidus /): [Unit Number]/[Street Number] [Street Name].

Example: Flat 2 at 14 Smith Street becomes 2/14 Smith St.

By allowing symbols like forward slashes and hyphens inside Address Line 1, you comfortably capture standard residential
layouts without needing to build separate, confusing fields for "Unit Type", "Unit Number", and "Street Number".

OIDC
With OIDC, authentication is delegated to an external Identity Provider (IdP) using OpenID Connect (OIDC).

This is the recommended method for production environments.

Users are managed in your external IdP and mapped through rules in Admin.
User groups can be managed in Admin or configured to use groups from your IdP.
Clients are managed in your external IdP and mapped through rules in Admin.

https://docs.camunda.io/docs/components/concepts/access-control/connect-to-identity-provider/#self-managed

Self-Managed
Self-Managed deployments only support external IdP integration using OpenID Connect (OIDC) (for example, Keycloak, Auth0, Okta, EntraID via OIDC).

You can integrate an IdP with both Admin (for the Orchestration Cluster) and Management Identity (for Web Modeler, Console, and Optimize).

export interface TaskResponse {
  userTaskKey: string;
  name: string;
  state: 'CREATED' | 'COMPLETED' | 'CANCELED' | string;
  assignee: string | null;
  processInstanceKey: string;
  completionDate: string | null;
  // ... other payload properties
}

@Component({
  selector: 'app-task-tracker',
  template: `...`
})
export class TaskTrackerComponent {
  private http = inject(HttpClient);

  /**
   * Polls the task endpoint using exponential backoff until `state === 'COMPLETED'`
   * or a terminal failure state is met.
   */
  pollTaskWithBackoff(userTaskKey: string): Observable<TaskResponse> {
    const INITIAL_DELAY_MS = 1000; // Start with a 1-second delay
    const MAX_DELAY_MS = 16000;    // Cap the maximum delay at 16 seconds
    let currentDelay = INITIAL_DELAY_MS;

    // Trigger the initial HTTP request immediately
    return this.http.get<TaskResponse>(`/api/tasks/${userTaskKey}`).pipe(
      expand((res) => {
        // Stop recursion when state is COMPLETED (or CANCELED)
        if (res.state === 'COMPLETED' || res.state === 'CANCELED') {
          return of(); // Returning empty observable stops `expand`
        }

        // Calculate delay for the next poll attempt
        const delayForNextAttempt = currentDelay;
        currentDelay = Math.min(currentDelay * 2, MAX_DELAY_MS);

        // Wait for `delayForNextAttempt` before firing the next request
        return timer(delayForNextAttempt).pipe(
          concatMap(() => this.http.get<TaskResponse>(`/api/tasks/${userTaskKey}`))
        );
      })
    );
  }

  startPolling(userTaskKey: string) {
    this.pollTaskWithBackoff(userTaskKey).subscribe({
      next: (task) => {
        if (task.state === 'COMPLETED') {
          console.log('Task finished successfully:', task);
          // Execute completion logic here
        } else {
          console.log(`Current state: ${task.state}. Retrying with backoff...`);
        }
      },
      complete: () => {
        console.log('Polling completed.');
      },
      error: (err) => {
        console.error('Error encountered while polling:', err);
      }
    });
  }
}

Use the number type to map to your Spring Boot JPA entities that use Long.JavaScript and TypeScript do not have a
dedicated 64-bit integer type like Java's Long. Instead, they represent all numeric data using standard 64-bit floating-point format.

Why number is Usually BestStandard Compatibility: Frontend tools, JSON serializers (like Jackson in Spring Boot), and
network protocols convert Java Long fields directly into standard JSON numbers.Range Safety: The number type safely
supports whole integers up to 9,007,199,254,740,991 (Number.MAX_SAFE_INTEGER). Database auto-incrementing IDs will not
exceed this limit for a massive amount of time.When to Use string InsteadIf your database IDs or Long fields can
exceed 9 quadrillion (for example, if you use Snowflake IDs, distributed systems UUID-like numbers, or complex hashing
algorithms), JavaScript will lose precision and round the numbers.The Fix: Configure your Spring Boot Jackson
serializer to output these fields as strings using @JsonSerialize(using = ToStringSerializer.class), and type them as
string in TypeScript.

The single most critical rule for Docker image tagging is to never rely on the latest tag for production deployments. Because the latest tag is inherently mutable and updates automatically when a newer image is pushed, using it results in unpredictable deployments, untraceable bugs, and broken rollbacks.An effective Docker tagging strategy balances human readability, absolute immutability, and automated traceability across your CI/CD pipelines.1. Versioning StrategiesSemantic Versioning (SemVer): Use the standard MAJOR.MINOR.PATCH format (e.g., 1.4.2). This helps consumers immediately understand whether an update introduces breaking changes, new features, or just bug fixes.Multi-Tagging Releases: Always assign multiple tags to the exact same image manifest. For example, when releasing version 1.4.2, apply all of the following tags simultaneously:myapp:1.4.2 (Strict patch specificity)myapp:1.4 (Tracks minor updates)myapp:1 (Tracks major updates)Environment Tags: Use descriptive markers like :prod, :staging, or :dev strictly for localized testing. However, avoid deploying to production using a moving tag like :prod; deploy the specific version tag instead.2. CI/CD and TraceabilityEmbed Git SHAs: Always tag your images with the specific Git commit hash that triggered the build (e.g., myapp:git-7b2a3f1). This provides a direct path from a running container back to the exact source code repository line.Build IDs & Timestamps: Pair the Git SHA with a build identifier or chronological timestamp (e.g., myapp:20260818.42-7b2a3f1). This makes sorting images easier and clarifies exactly when an image was compiled.Automate via Registry Pipelines: Never tag production images manually. Configure your workflows (like GitHub Actions, GitLab CI, or Cloud Build) to apply tags automatically during the compilation process.3. Registry Governance & SecurityEnforce Immutability: Enable "Tag Immutability" within your cloud registry settings (e.g., AWS ECR or Azure Container Registry). This prevents developers or automated pipelines from accidentally overwriting an existing version tag.Utilize Content Digests: For mission-critical environments where absolute security is required, pull images using their immutable SHA256 cryptographic digest instead of a tag (e.g., myapp@sha256:cb4b...). Tags can be altered, but digests cannot.Prune with Retention Policies: Set up automated registry cleanup rules. Retaining every single development tag quickly fills up storage and spikes costs; configure policies to automatically purge untagged images or artifacts older than 30 days.4. Base Image SelectionPin Your Base Images: When building custom applications, avoid using unversioned parent components inside your Dockerfile (e.g., FROM node:latest). Always pinpoint specific tags down to the minor release and OS variant (e.g., FROM node:20.11-alpine) to prevent upstream changes from breaking your application.

## Docker Compose

We provide the following Docker Compose files that are useful during development and testing:

| Component                                                 | Description                                             |
|:----------------------------------------------------------|:--------------------------------------------------------|
| serendipity-identity-service.yml                          | Lightweight Serendipity Identity Service configuration. |
| serendipity-identity-service-export-development-realm.yml | Export the Development Realm.                           |
| serendipity-identity-service-import-development-realm.yml | Import the Development Realm.                           |

### Start the Serendipity Identity Service

To start the Serendipity Identity Service locally, in the project's `/backend` directory, run

```
docker compose -f serendipity-identity-service.yml up -d
```

### Stop the Serendipity Identity Service

To stop the containers, run:

```
docker compose -f serendipity-identity-service.yml stop
```

### Export the Development Realm

To export the Development Realm, run:

```
docker compose -f serendipity-identity-service-export-development-realm.yml up -d
docker compose -f serendipity-identity-service-export-development-realm.yml down -v
```

:::info

Look for a file named `development-realm.json` in the `/backend` directory.

:::

### Import the Development Realm

To import the Development Realm, run:

```
docker compose -f serendipity-identity-service-import-development-realm.yml up -d
```


#### Import a Realm

Keycloak can import a realm when it starts up.

For example:

```
    ...

    command:
      [
        "start-dev",
        "-Dkeycloak.migration.action=import",
        "-Dkeycloak.migration.provider=singleFile",
        "-Dkeycloak.migration.realmName=serendipity-dev",
        "-Dkeycloak.migration.strategy=OVERWRITE_EXISTING",
        "-Dkeycloak.migration.file=/import/development-realm.json"
      ]

    ...

    volumes:
      - "${PWD}:/import"
      - "${PWD}:/export"
```

#### Export a Realm

Keycloak can export a realm when it starts up.

For example:

```
    ...

    command:
      [
        "start-dev",
        "-Dkeycloak.migration.action=export",
        "-Dkeycloak.migration.provider=singleFile",
        "-Dkeycloak.migration.realmName=serendipity-dev",
        "-Dkeycloak.migration.usersExportStrategy=REALM_FILE",
        "-Dkeycloak.migration.file=/export/development-realm.json"
      ]

    ...

    volumes:
      - "${PWD}:/import"
      - "${PWD}:/export"
```

The error occurs because the PostgreSQL docker entrypoint script automatically runs a chown command on everything
inside the data directory to ensure permissions are secure. Because your certificates are mounted as :ro (Read-Only)
from your host machine, the container fails when trying to change their ownership, throwing Read-only file system and
crashing with code 1.To resolve this completely, you must mount the certificates outside of the main database folder
so PostgreSQL doesn't try to change their permissions, while still matching the strict file permission rules (0600)
required for SSL keys.

1. The Issuer URI Split (The Biggest Gotcha)When your BFF boots up, spring-security contacts Keycloak to fetch its OpenID configuration (.well-known/openid-configuration).The Problem: If you configure the BFF to look at https://serendipity.localhost..., the BFF container will fail because it cannot resolve serendipity.localhost internally. If you configure it to use http://serendipity-identity-service:8080/auth/..., Keycloak will generate token signatures with that internal URI. When the user's browser later tries to log in using https://serendipity.localhost, Spring will reject the token because the issuer strings don't match.The Solution: You must separate the Issuer URI (what the token claims state) from the JWK Set URI (where the BFF actually goes to fetch the public keys internally).2. Nginx Protocol Awareness (server.forward-headers-strategy)Because Nginx handles the public SSL certificate (https) and passes plain http to your BFF container, Spring needs to be explicitly told to read the X-Forwarded-Proto and X-Forwarded-Port headers you set in Nginx. If you omit this, Spring will generate OAuth2 redirect URIs using http:// instead of https://, breaking the login flow.3. Token Propagation (TokenRelay)As a BFF, the gateway should manage the user's session via a secure cookie, strip that cookie when a request matches a route, and automatically inject the raw Keycloak Bearer <JWT> token into the downstream microservices (like party-service).

efault, but there is a major problem with how Spring Boot parses the traditional setup when dealing with your Nginx reverse proxy architecture.

When you provide only an issuer-uri, Spring Boot automatically performs a discovery step. Behind the scenes, the BFF container will make a network request to:https://serendipity.localhostThis will immediately crash your BFF container with a UnknownHostException or connection timeout. Why? Because inside the isolated Docker network, the serendipity-web-bff container has no idea what serendipity.localhost is. Only your computer's web browser understands that domain.

The discovery step works, but when a user logs in, Keycloak creates a cryptographically signed token stating: "I am http://serendipity-identity-service:8080...". When the user's browser redirects back to the BFF via Nginx, Spring Boot will compare the incoming token issuer string with what it expects. Because https://serendipity.localhost does not match http://serendipity-identity-service, Spring Boot will reject the token with an authentication error.🛠️ The Correct application.yml Provider SetupTo solve this split-network problem, you must provide Spring Boot with the specific configuration blocks in your application.yml to override the auto-discovery URLs.By explicitly specifying the internal endpoint paths, you satisfy Spring Boot's requirement to look in the application.yml while bypassing the Docker network routing restrictions.Add this exact structure to your application.yml:

What this achieves:authorization-uri: This is a public redirect. The BFF hands this directly to the user's browser, so it correctly points to the external https://serendipity.localhost via Nginx.token-uri / jwk-set-uri: These are server-to-server calls. The BFF makes these calls directly over the fast, internal Docker network (http://serendipity-identity-service:8080) without needing to route out to the internet or handle local domain mapping.issuer-uri: Used purely as a string check to match the signatures inside the JWT tokens.

  openssl pkcs12 -export \

  sudo chmod 600 *.p12
