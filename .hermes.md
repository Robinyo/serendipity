# Serendipity — Project Knowledge Layer

This repo keeps its canonical project knowledge in `.knowledge/`
(the Open Knowledge Format monorepo). The Docusaurus docs site lives in
`website/docs/` and is a separate, rendered layer — consult `.knowledge/` first
for project-level facts, decisions, and architecture; use `website/docs/` for
procedural, how-to, and component-level documents.

## Knowledge layer

The following files in `.knowledge/` are the single source of truth for the
topics they cover. When answering a question about the project — architecture,
decisions, security model, frontend/backend structure, runtime topology —
read the relevant `.knowledge/` file(s) first. Do not answer from memory about
facts that are documented there. If the knowledge layer does not yet cover a
topic, say so and offer to expand it (writing a new `.knowledge/` file or
deferring to `website/docs/`).

| File | What it is |
|---|---|
| `.knowledge/index.md` | Global monorepo map and entry point |
| `.knowledge/log.md` | Architecture decision log — ADR-0001 through ADR-0005 |
| `.knowledge/backend/index.md` | Spring Boot backend architecture: modules, build, runtime topology, how the pieces fit |
| `.knowledge/backend/security.md` | Security model: Keycloak, two-token model, roles, groups, `manager` attribute, enforcement |
| `.knowledge/frontend/index.md` | Angular 22 + BFF flow + token relay + `/api.me` |
| `.knowledge/integration/api-contracts.md` | API contract layer (placeholder in v1; current surface + target state) |

## Source-of-truth rules (current)

- **Party Service entity model** — `Party`, `Organisation`, `Individual`, and their
  related entities (as shipped in `backend/modules/party-service/`) are the source
  of truth. ADR-0005 captures this. The entity-model details live in
  `backend/modules/party-service/` (entities, repositories, services, controllers).
- **No Serendipity `User` table** — users are Keycloak users only. Keycloak's default
  managed attributes (`username`, `email`, `firstName`, `lastName`) are the identity
  attributes. Custom Keycloak user attributes hold project-specific fields
  (e.g. `manager`, storing the manager's `sub`).
- **Identity attributes live in the ID token** — `username`, `email`, `firstName`,
  `lastName`, and other profile attributes are carried by the ID token (and the
  userinfo endpoint). The access token the BFF forwards to services carries
  `sub` + `realm_access.roles` + `groups` (and whatever User Attribute mapper emits,
  e.g. `manager`) for enforcement. The access token still contains `sub`, so services
  can do ownership / assignment comparisons.
- **`username`, not `preferred_username`** — the Keycloak user attribute to reference is
  `username` (one of the four default managed attributes). `sub` is the system-generated
  stable identifier (a Keycloak UUID), not a configurable user profile attribute.
- **`manager` attribute** — a custom Keycloak user attribute whose value is the manager's
  `sub`. Today it is set manually via the Admin Console's Attributes tab (copy the
  manager's `sub` from one user's Details tab into another user's Attributes tab).
  No built-in "look up a manager by username and store their `sub`". Enterprise
  deployment typically federates to MS Entra ID — federation changes where the
  `manager` value comes from and how it's mapped, not what the value means.
- **`roles?: string[]`** — this is a PWA concept, not a Keycloak user attribute; it is
  the BFF-supplied view of the user's roles for the frontend (the frontend has only a
  cookie, not the token).

## Open items (write or defer as appropriate)

- `frontend/state-mgmt.md` — deferred; read the Angular state code before writing.
- `integration/api-contracts.md` — placeholder; the current Party Service endpoint
  surface and the BFF `/api.me` contract shape are not yet enumerated in the
  knowledge layer.
- `backend/services/` tree and additional backend services — as the project grows past
  the BFF and Party Service, additional modules would be added to the parent POM and
  the runtime topology.
- Party Service resource-server support — currently the Party Service trusts the BFF
  as its security boundary (ADR-0004); making it an OAuth 2.0 resource server is
  open work.

## Two-layer model

- `.knowledge/` — canonical knowledge layer; project facts, decisions, architecture.
- `website/docs/` — Docusaurus source; rendered at
  `https://robinyo.github.io/serendipity`. Procedural, how-to, component-level docs.
